# Decisions and limits

**Small core.** PHP 8.3, PDO/MySQL 8, Composer and PHPUnit. Yii2 adds little to five HTTP flows, so responsibilities are separated in small classes instead. MySQL is authoritative; SQLite belongs only to the mock. UTC defines the day (hard-coded in code, not configurable). Amounts are two-decimal strings/DECIMAL, never floats. Canonical identities are case-sensitive and opaque; SMS destinations are separate.

**One daily payment.** The external key is SHA-256 hex of an unambiguous JSON tuple `(daily-pass-v1, applicationId, canonicalIdentity, billingDay)`, persisted before HTTP and reused on retries. Unique database constraints enforce `(subscriber_id,billing_day)` and the key. The supplied contract specifies no key format limit; the mock accepts 64 hex characters. A real carrier's undocumented restrictions need confirmation.

**STOP and concurrency.** Lifecycle, billing and SMS share a connection-scoped MySQL advisory lock per identity, held across HTTP; short transactions also use row locks. Billing rechecks ACTIVE after acquiring the lock. STOP commits INACTIVE before remote unsubscribe. Delayed REGISTERED cannot clear its tombstone. An already dispatched debit cannot be cancelled; STOP waits for that critical section. No debit starts after STOP completes. This assumes one MySQL writer, without distributed fencing during failover. Failed remote unsubscribe requires repeat STOP; local billing stays disabled.

**Payment policy.** `PENDING → PROCESSING → SUCCEEDED | RETRY_SCHEDULED | FAILED_PERMANENT | EXHAUSTED | UNKNOWN`. Only E1326/E1318 retry: 60s/120s backoff, three attempts total, within the original UTC day; old pending retries become EXPIRED. E1308 suspends. E1337, unexpected responses and transport uncertainty become UNKNOWN, blocking all further automatic debits for that identity. Reconciliation requires external ledger evidence: this contract has no lookup API.

**Crash boundary.** Before committing PROCESSING, PENDING is safe to resume. Any crash after that commit conservatively recovers to UNKNOWN, including a crash before HTTP. Confirmed success and receipt outbox commit atomically. A restart drains pending SMS; a crash after delivery but before marking SENT can duplicate SMS because its API has no idempotency key. This is not exactly-once execution.

**Deliberate limits.** Manual jobs need periodic scheduling for retries/outbox. Grace preserves ACTIVE through the billing day. Event fingerprints use identity/status/timestamp because no event ID exists; stale events are ignored. Aliases require a consistent canonical identity and explicit SMS routing, since no mapping API exists. Auth/SSO, multiple currencies, USSD, DLR, balance queries, production infra and polished UI are excluded. The PHP multiworker server and shared generated secret volume are local demo infrastructure. Detailed scenarios and crash behavior are in README; actual verification and the Docker access blocker are in VERIFICATION.md.
**Known gaps.** (1) Webhook authentication is only the `applicationId` field; there is no shared secret or signature, so callbacks are spoofable by anyone who knows it. (2) `UNKNOWN` payments block that subscriber's debits until manual reconciliation against carrier evidence; there is no admin/reconciliation endpoint. (3) Retries and the SMS outbox run only when `/jobs/bill` or `/jobs/sms` is triggered; there is no built-in scheduler. (4) A masked alias uses a non-`tel:` form (for example `alias:...`) and needs an explicit `smsDestination` to receive SMS. (5) `/jobs/bill` isolates per-subscriber failures and reports `BUSY` or `ERROR` for them; failed items are only retried on the next trigger.

**Manual test UI and CORS.** `GET /` on the service serves a single static page (`service/public/ui.html`, vanilla JS, no build) for manual scenario testing; it calls the mock at port 8081 from the browser, so both the service and the mock send `Access-Control-Allow-Origin: *` (allow header `Content-Type`) and answer `OPTIONS` with 204. This is acceptable only because both ports bind to loopback and the mock is an unauthenticated demo admin; do not carry it to a real deployment.
